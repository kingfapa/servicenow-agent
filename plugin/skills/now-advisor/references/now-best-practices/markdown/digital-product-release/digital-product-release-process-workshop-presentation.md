## Slide 18

Be the release process orchestrator, enabling Product teams to consistently plan and deliver new versions of products by providing visibility into the release process and automating the validation of “release readiness” with minimal overhead.

Vision for Digital Product Release

### Speaker notes

DPR is designed to help organizations manage the process in which they ensure products are ready to deploy…DPR does NOT encompass capabilities to actually do the development, testing, or deployment.

Release Management, as a whole has, been shifting away from central teams doing everything as it can significantly slow down the pace of releases and innovation

Central teams now are more focused on defining governance and policies for distributed, product teams to follow and have their work released in a compliant and resilient fashion

This is where we want DPR to play - providing central release teams the ability to define reusable controls to ensure compliance with minimal overhead.

### Speaker notes

As stated, DPR does NOT encompass capabilities to do the build, testing, or actual deployment of a product – what it does do is tie these phases together (from planning to deployment) as the layer validating when a product is ready to progress from one stage to the next via policy checks.

Policies are data-driven validation checks that happen automatically, leveraging data from records and 3rd party integrations

Think of policies as the “gates” that deem when a release is ready to progress from one phase to the next. Only once all policies tied to a particular phase are compliant can a product move to the next phase.

You may also notice the concept of “tasks” – tasks are designed to explicitly be looked at by a human, so manual checks to cover needed actions like gaining legal approval or design sign-off.

Tasks are not what are used to determine if a product can progress to the next phase – that said, there is a policy that checks to see that all tasks are complete and this could be associated to one, a few, or all phases

At the bottom of the visualization, you’ll see many 3rd party CI/CD planning, orchestration, security, and monitoring tools that can be leveraged w/ DPR in policy checks.

DPR is leveraging the DevOps data model to integrate with these tools.

Note: DPR does not require DevOps Change to use

Historically ServiceNow has focused on the last mile - so what needs to happen just before deployment. This is where customers created changes with tons of custom checks to validate if code is ready to push to production. (DCV automated this creation and approval)

DPR is shifting those same checks left to ensure a broader range of criteria are met and validated at the times the happen before a change is logged and code deployed.

## Slide 41

Multi-product release

Many customers manage releases comprised of several products, whether a release of a “parent” product with “child” enabling products, or a release encompassing various interdependent products

DPR supports the creation and management of a single release that encompasses multiple products. Customers can manage a single release with all these products within it and manage the release execution of the underlying products at both the aggregate and individual levels.

### Speaker notes

Explain and Discuss

================

Customers have provided feedback on the need to manage complex releases that span multiple products and have inter dependencies

Guided release creation experience to help customers create a release with the relevant products, versions, templates, and target dates

Manage release execution (e.g., task and policy compliance) both at the aggregate, multi-product, level and at the individual component product level

Gain visibility into release readiness status across all products in the release

​​Solution​​

For release creation, have a guided experience that walks users through defining the release details, associating the relevant products and software versions for the release, associating the relevant release template(s), and finally picking the release target go-live date.

Users can select a single product or multiple products to create a release against

For release execution, experience will have two “modes”: individual product and aggregate release

Individual experience is like that of the current single product release – see relevant tasks, policies, release phases, status, etc. for the individual component product

Aggregate experience shows the task and policy status across all products in the release. Only in this mode can users retarget the release date or restart a phase of a release

Visibility into release execution status at the aggregate and individual product level

Gain visibility into release readiness status across all products in the release

​​Solution​​

For release creation, have a guided experience that walks users through defining the release details, associating the relevant products and software versions for the release, associating the relevant release template(s), and finally picking the release target go-live date.

Users can select a single product or multiple products to create a release against

For release execution, experience will have two “modes”: individual product and aggregate release

Individual experience is like that of the current single product release – see relevant tasks, policies, release phases, status, etc. for the individual component product

Aggregate experience shows the task and policy status across all products in the release. Only in this mode can users retarget the release date or restart a phase of a release
