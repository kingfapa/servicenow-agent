## Slide 19

ServiceNow definitions for common terms:

Problem: The underlying cause of one or more incidents. The root cause is not known at the time a problem record is created, and the Problem Management process is responsible for further investigation.

Known Error: Where an issue has been identified a Known Error knowledge article can be created to publicize the issue.

Root Cause: The underlying or original cause of an incident or problem.

Workaround: A temporary way to restore service failures to a usable level.

Definitions

### Speaker notes

Explain and discuss

Reiterate the point that this is not a strict ITIL version of the process and therefore some terms that customers are familiar with may not 100% match their current understanding

It is key to point out that our definition of a Known Error is not ITIL aligned.  Our experience over many years of implementations shows us that the majority of customers also prefer not to use this same tight definition.  The critical difference is that a Known Error does not have to have a workaround or an identified root cause in order to exist. It is perfectly possible for an error to have been identified without either of these things and that is extremely commonplace in most organizations

## Slide 21

Problem Management process lifecycle

### Speaker notes

Explain and discuss

Explain that this is the out-of-the-box lifecycle

Explain that this state model has been designed to offer the simplest process and is based on ServiceNow’s years of experience in the industry.  This is our recommended industry proven practice

Explain that even the most complex customers should not need to change this flow

Explain that our core process is very simple and that is a deliberate design decision to try to move customers away from unnecessary and complex customizations.  Experience shows us that many customers who believe they needed to add more complexity to this process have since tried to remove it

Detection and Logging (New &amp; Assess)

Detect a problem proactively or reactively

Create a new problem record and documents known details

Prioritize and categorize the problem

Assign the investigation to group/individual

Investigation and Diagnosis (Root Cause Analysis , Fix in Progress)

Conduct a root cause analysis (RCA) to determine the underlying cause of the incident(s)

Create problem tasks, as needed

Document root cause, workaround, and fix

Create Known Error document, if needed

Resolution and Closure (Resolved , Closed)

Confirm workaround or fixe restores service for related incidents

Implement change to permanently remove root cause, if required

Update Known Error document, if applicable

Update and close problem record

Recommend

Strongly push the customer to remain with this state model – there must be very compelling reasons to use a different one since they will be misaligned to the future process design

State model is managed in State Management -&gt; State Models

## Slide 23

Process flow – State: New – Assess

### Speaker notes

Explain and discuss

New State

Explain that very basic information is added at this stage that may suggest a problem exists and would be worth looking into.  All known information about the symptoms experienced is captured

Explain that the appropriate assignment group (a Problem Management group) is assigned to assess the problem in the next phase of the lifecycle

Assess State

Explain that the Problem Coordinator is primarily assessing the record to determine whether it is a genuine problem or not

Explain that if it is not a genuine problem the record is canceled with an explanation

If a duplicate record is found the problem is closed as a duplicate with the duplicated record related

Explain that the Problem Coordinator will add additional information and prioritization to the record once they have established it is worth investigating

## Slide 24

Process flow – State: Root cause analysis

### Speaker notes

Explain and discuss

Explain that Root Cause Analysis state is where the bulk of the work is conducted.  Here the root cause is investigated.  A workaround may also be uncovered and if so this can be published to any related incidents.  Finally the root cause is identified although it is possible for the root cause to be too difficult to figure out

Explain that the Problem Coordinator may feel the problem is high impacting enough that it requires additional visibility in which case a Known Error Article be published in the knowledge base.  This can happen at any time regardless of whether a workaround or the root cause have been discovered

Explain that if the problem has been investigated however no workaround or root cause can be identified, or a fix may have been found but the cost/effort/impact of implementing it is considered too high then the Problem Coordinator can set the problem to Risk Accepted which will move the record to Closed state.

Explain that the Problem Coordinator will need to engage one or more technical support teams to investigate the problem at Root Cause Analysis state

The Problem Coordinator retains ownership and responsibility for all problems

The problem record remains assigned to the Problem Coordinator throughout the entire process

The Problem Coordinator assigns individual tasks out to the various technical support teams to conduct the investigation and diagnosis

Each team will capture their own investigation and discoveries in their individual tasks and the Problem Coordinator will review them all

The Problem Coordinator is responsible for updating the parent problem record with information from the tasks

## Slide 25

Process flow – State: Fix in progress – Resolved – Closed

### Speaker notes

Explain and discuss

Fix in Progress state:

Fix in Progress state is where the fix identified in the previous state is implemented

At this state change should be raised

If the fix does not work and it is deemed not worth spending further effort on the fix the problem can be set to Risk Accepted which will move the record to Closed state

Unlike the incident management process the intention with problem is not to close down the record as quickly as possible.  The goal is to permanently fix the error no matter how long that may take.  Therefore customers should feel comfortable leaving problem records open indefinitely

Resolved state:

In Resolved state the method of resolution is captured in the Fix Notes field

Problem Coordinator can conduct any review activities at this point by creating further tasks for action

Once a review is completed the Problem Coordinator will confirm the problem is definitely resolved.  If this is not the case they will set the problem back to Root Cause Analysis state

Closed state:

no activities are expected to take place

it is possible for a Problem Coordinator to reopen the problem if required or simply make updates to the problem record. The main use case for this would be if the problem was difficult to reproduce and was thought to be fixed however later on reoccurred
